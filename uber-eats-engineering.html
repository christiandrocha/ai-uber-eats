01

The problem the pipeline solves

Problem 1

Payment data arrives mixed with GPS, order, restaurant, and driver events — all in the same Volume, with no separation.

Problem 2

Timestamps arrive in scientific notation (1.7596E12), which Spark infers as Double — causing silent precision loss at the millisecond level.

Problem 3

A payments team needs to know: what is the capture rate? How long does each stage take? Which payments are stuck?

The answer: A Medallion Architecture with three layers. Each layer has a single, clear responsibility — ingestion, quality, or analytics. None of them do all three at once.

03

Engineering problems solved

Decision 01

Scientific notation in timestamps

Spark infers 1.7596876023E12 as DoubleType
→ 1759687600000.0 (loses milliseconds)
Explicit schema with LongType forces the JSON reader to cast the float to integer correctly. Validated in a sanity-check cell in the Bronze notebook.
Decision 02

Volume with multiple event types

NULL = NULL is FALSE in SQL
→ null event_ids enter the MERGE as "unmatched"
→ accumulate 127K null records per run
Filter event_id IS NOT NULL AND payment_id IS NOT NULL AND event IS NOT NULL before the MERGE. Records from other domains are dropped at Bronze.
Decision 03

Reprocessing without duplicates

APPEND mode duplicates data if the same file
is processed twice (retry, reprocessing)
MERGE ON event_id across all layers. Bronze: only inserts new event_ids. Silver: updates if _ingested_at is more recent. Gold: updates all fields by payment_id.
Decision 04

Avoid full Bronze scan on every run

Reading 500K+ records in full on every run
→ slow and expensive as Bronze grows
Silver uses a watermark: _ingested_at > MAX(silver._ingested_at). First run reads everything. Subsequent runs read only what arrived after.
Decision 05

Bad data passing silently

Without an alert, 100% of records could be
quarantined with nobody noticing.
The pipeline "passed" but Gold was empty.
check_quarantine_rate() raises ValueError if the quarantine rate exceeds 15% (calibrated above the 10.3% known-bad source baseline). The job fails before writing — surfacing the problem instead of degrading silently.
Decision 06

Partitioning creates small files

PARTITIONED BY generates many small files
→ slow queries, high metadata cost
→ hard to rebalance later
CLUSTER BY (Liquid Clustering) — Delta reorganizes files automatically on compaction. Adapts to query patterns without manual repartitioning.
Decision 07

event.timestamp absent for non-created events

Source JSON omits the epoch timestamp field for
authorized, captured, closed, succeeded, settled,
refunded — Rule 5 quarantined 2,086 of 2,462 rows (85%)
Silver resolves event_timestamp via COALESCE: epoch field first, dt_current_timestamp as fallback. Quarantine fires only when both are absent — no usable time reference at all.
Decision 08

VALID_EVENT_NAMES too narrow

Initial gate only allowed created / authorized / captured.
Real lifecycle has 7 event types — closed, succeeded,
settled, refunded were quarantined as "invalid", causing
54% quarantine rate and Gold columns full of nulls.
Expanded VALID_EVENT_NAMES to all 7 lifecycle values after inspecting Bronze. Quarantine threshold raised from 5% to 15% — calibrated above the 10.3% known-bad baseline (254 structurally empty source rows).
Decision 09

Watermark stale after same-batch Bronze ingestion

All 2,462 Bronze records shared the same _ingested_at.
Silver incremental filter (> MAX(_ingested_at)) returned
zero rows on every re-run after the initial 376 were written.
TRUNCATE TABLE silver_payment_events resets the watermark to null, forcing a full Bronze read on the next run. Required once whenever Bronze is back-filled in a single batch.
04

Why extract to a Python package?

The notebooks had all logic inline. The tests copied that logic to test it — which means a bug in the notebook wouldn't be caught by the test (they were testing copies, not the real code).

Extracting to src/uber_eats/ solves this: notebooks import the functions, tests import the same functions. Any change to the code is automatically tested.

▣ bronze.py
  • add_metadata_columns()
  • validate_structure()
  • merge_dedup()
▣ silver.py
  • apply_quality_gate()
  • apply_transformations()
  • deduplicate()
  • silver_merge_dedup()
  • check_quarantine_rate()
▣ gold.py
  • build_gold()
  • gold_merge()
Result: 75 tests, 100% coverage, running locally with PySpark without needing a Databricks connection. Each business function is tested with real data (local PySpark session), not mocks.

06

dbt — Gold Layer

gold_payment_summary
One row per payment_id — lifecycle timestamps, status, timing metrics
Incremental MERGE on payment_id — only recomputes payments with new Silver activity
Tests: unique, not_null, accepted_values + custom assert_no_negative_times
-- models/gold/gold_payment_summary.sql
SELECT
  payment_id,
  MAX(CASE WHEN event_name = 'created'   THEN event_timestamp END) AS created_at,
  MAX(CASE WHEN event_name = 'authorized' THEN event_timestamp END) AS authorized_at,
  MAX(CASE WHEN event_name = 'captured'  THEN event_timestamp END) AS captured_at,
  MAX(CASE WHEN event_name = 'settled'   THEN event_timestamp END) AS settled_at,
  -- + closed_at, succeeded_at, refunded_at
  CASE WHEN settled_at   IS NOT NULL THEN 'settled'
       WHEN captured_at IS NOT NULL THEN 'captured'
       ELSE 'created' END AS payment_status
FROM {{ source('payments', 'silver_payment_events') }}
GROUP BY payment_id
mart_payment_daily_kpis
One row per calendar day — capture rate, avg auth/capture/total times
3-day incremental lookback absorbs late-arriving events
Tests: unique(payment_date), not_null — added as a plain .sql file, no notebook
-- models/gold/mart_payment_daily_kpis.sql
SELECT
  DATE(created_at) AS payment_date,
  COUNT_IF(payment_status = 'captured')
    * 100.0 / COUNT(*) AS capture_rate_pct,
  ...
FROM {{ ref('gold_payment_summary') }}
GROUP BY DATE(created_at)
Architecture: Bronze and Silver stay in PySpark — dbt is SQL-first and doesn't handle file ingestion or Python-based quarantine logic. The stack is Bronze (PySpark) → Silver (PySpark) → Gold (dbt) → Marts (dbt). Each tool where it shines.
